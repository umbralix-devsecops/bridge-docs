== Antes de empezar

Cuatro herramientas. Comprueba las versiones: los tres fallos más comunes del primer arranque son un SDK 8 heredado de la guía de onboarding del portal (desactualizada; `ADR-BS-009`), un Node anterior a 22.12 y Docker sin arrancar.

[cols="1,1,2",options="header"]
|===
| Herramienta | Versión | Comprobación

| .NET SDK | **10.x** | `dotnet --version` → `10.0.…`
| Docker Desktop (o Engine + Compose v2) | cualquiera reciente | `docker compose version` y `docker ps` sin error
| `dotnet-ef` | 10.x | `dotnet ef --version`. Si falta: `dotnet tool install --global dotnet-ef`
| Node.js (solo para el frontend) | **≥ 22.12** | `node --version`
| `openssl` (una vez, para la clave JWT) | cualquiera | En Windows viene con Git for Windows; úsalo desde Git Bash
| `gitleaks` (opcional) | — | La CI lo ejecuta; `verify.sh` avisa si no está
|===

Repositorios, hermanos en la misma carpeta — las rutas relativas de los scripts y del README lo asumen:

[source]
----
portal-videos/
├── Sin-PortalBridge/     ← este servicio
├── Sin-PortalVideos/     ← frontend Angular
├── bridge-docs/          ← esta documentación
└── portal-docs/          ← documentación del portal (contratos api_*.yaml viven en Sin-PortalVideos/openapi/sources)
----

[source,bash]
----
git clone https://github.com/Devs-Umbralix/Sin-PortalBridge.git
git clone <url>/Sin-PortalVideos.git
git clone <url>/bridge-docs.git
cd Sin-PortalBridge
----

== Configuración local (una sola vez)

=== La cadena de conexión y el resto de ajustes no secretos

[source,bash]
----
cp src/BridgeService.Api/appsettings.Development.json.example \
   src/BridgeService.Api/appsettings.Development.json
----

El archivo copiado está en `.gitignore` (`SEC-BS-01`). Apunta a `localhost:5432`, base `bridge`, usuario `bridge`, contraseña `bridge_dev_only` — exactamente lo que levanta el `compose`. No hace falta tocar nada más para arrancar.

=== La clave de firma de los JWT

Es el único secreto real. Va a *user-secrets*, que viven fuera del árbol de trabajo (`%APPDATA%\Microsoft\UserSecrets\bridge-service-portal-videos\` en Windows, `~/.microsoft/usersecrets/…` en Linux/macOS).

[source,bash]
----
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:2048 -out clave-dev.pem
dotnet user-secrets --project src/BridgeService.Api set "Jwt:PrivateKeyPem" "$(cat clave-dev.pem)"
rm clave-dev.pem
----

[NOTE]
Sin ella el servicio arranca pero el primer `POST /auth/login` falla con un mensaje que dice exactamente esto. En Azure la misma clave de configuración llega desde Key Vault; el código no distingue.

=== La credencial de ingesta

`POST /v1/ingest/catalog` exige un token de servicio, que a su vez exige `Ingest:ClientId` y **el resumen SHA-256** de un secreto. El secreto se genera, nunca se teclea. En Git Bash o Linux:

[source,bash]
----
secreto=$(openssl rand -base64 32 | tr -d '=' | tr '+/' '-_')
resumen=$(printf '%s' "$secreto" | openssl dgst -sha256 -binary | base64 | tr -d '=' | tr '+/' '-_')
echo "secreto=$secreto"
echo "resumen=$resumen"
----

(El `.example` trae el equivalente en PowerShell.) El **resumen** va a `Ingest:ClientSecretHash` en `appsettings.Development.json`, sustituyendo a `<pega aqui el resumen>`. El **secreto** lo guardas tú: es lo que presentará el cliente de ingesta en §7. `ClientId` puede quedarse en `ingest-simulator-local`.

=== El almacenamiento de recursos: Azurite (`T-BS-071`)

El proxy de streaming lee los bytes de Azure Blob Storage; en local, de **Azurite**, su emulador oficial, que el `compose` levanta. El `.example` ya trae la cadena:

[source,json]
----
"Storage": {
  "ConnectionString": "UseDevelopmentStorage=true",
  "AccountUri": "http://localhost:10000/devstoreaccount1",
  "PublicContainer": "media-public",
  "PrivateContainer": "media-private"
}
----

Si tu `appsettings.Development.json` es anterior a la Fase 7, añade la línea `ConnectionString`. Sin ella el servicio arranca igual —la Entrega 1 no toca el almacenamiento— y el primer `GET /media/{id}/stream` falla con un mensaje que dice qué falta. En Azure **no** hay cadena: la identidad administrada del servicio con el rol `Storage Blob Data Reader` sobre la cuenta (`DEC-BS-15`), y solo `AccountUri` en configuración.

=== Enlace de invitación (`DEC-BS-25`)

`Frontend:BaseUrl` ya viene como `http://localhost:4200` en el `.example`. Con él se compone `…/set-password?token=…` del correo que recibe un usuario creado por administrador. Si falta, `POST /admin/users` falla con un mensaje explícito y el arranque avisa.

=== Límites de login y registro (`T-BS-092`)

`POST /auth/login` admite 20 peticiones por minuto e IP, y `POST /auth/register`, 5 cada diez minutos (`api_auth.yaml` 1.2.0). Pasado el tope, la respuesta es `429 RATE_LIMITED` con `Retry-After`. En local todo llega desde la misma IP, así que el `.example` los sube:

[source,json]
----
"Auth": {
  "RateLimit": {
    "LoginRequestsPerMinutePerIp": 1000,
    "RegisterRequestsPer10MinutesPerIp": 1000
  }
}
----

Si tu `appsettings.Development.json` es anterior al 2026-09-25, añade la sección. Sin ella valen los de producción, y una tanda de pruebas a mano o de Playwright contra una API que arrancaste tú acaba en `429`. `dev-up.sh`, `e2e-entrega1.sh` y `e2e-entrega2.sh` no dependen de esto: fijan los dos valores por variable de entorno.

== Levantar la infraestructura

[source,bash]
----
docker compose up -d postgres mailpit azurite
docker compose ps
----

Espera a que `postgres` esté `healthy`. Qué hay:

[cols="1,1,3",options="header"]
|===
| Servicio | Puerto | Para qué

| `postgres` (16-alpine) | 5432 | La base. Volumen `postgres-data`: sobrevive a `down`; `down -v` la borra.
| `mailpit` | 1025 SMTP · **8025 web** | Buzón de desarrollo. Acepta todo y no entrega nada. Ahí aparecen los correos de registro, aprobación e invitación: `http://localhost:8025`.
| `azurite` | 10000 | Azure Blob Storage en local (`T-BS-071`). Cuenta `devstoreaccount1`, credencial pública por diseño. Volumen `azurite-data`. Los contenedores `media-public` y `media-private` los crea el simulador (`upload-blobs`).
| `api` | 8080 | La API **en contenedor**. Para desarrollar no la uses: `dotnet run` (§5) recarga y depura; el contenedor sirve para probar el `Dockerfile`.
|===

[TIP]
`docker compose up -d` sin nombres levanta también `api`, que compila la imagen (minutos) y necesita `JWT_PRIVATE_KEY_PEM` e `INGEST_CLIENT_SECRET_HASH` en un `.env`. Para el día a día, levanta `postgres`, `mailpit` y `azurite`.

== Base de datos: migraciones y semilla

[source,bash]
----
dotnet restore
dotnet ef database update -p src/BridgeService.Infrastructure -s src/BridgeService.Api
----

`dotnet ef` no arranca la aplicación: usa `AppDbContextFactory`, que fija Development y lee la cadena de `appsettings.Development.json`. Aplica en orden `MIG-BS-001` (esquema, particiones, GIN, **semilla de 4 roles y 24 permisos** desde `003_seed_roles.sql`), `MIG-BS-002` (índices), `MIG-BS-003` (administración de usuarios), `MIG-BS-004` (`config:read` del editor) y `MIG-BS-005` (reintentos de la cola de notificaciones).

Comprobación rápida:

[source,bash]
----
docker compose exec postgres psql -U bridge -d bridge -c "SELECT name FROM roles ORDER BY 1;"
docker compose exec postgres psql -U bridge -d bridge -c "SELECT count(*) FROM __efmigrationshistory;"   # → 5
----

[IMPORTANT]
El esquema se cambia **solo** por migraciones de EF Core (`ADR-BS-004`, `DOM-BS-04`). `schema_derivado_v2.sql` es un artefacto derivado para leer, nunca para ejecutar. Nueva migración = nueva entrada `MIG-BS-NNN` en `changelog_modelo_datos.adoc` en el mismo commit (`DOM-BS-05`); `ArchitectureTests` lo comprueba.

== Arrancar el servicio

[source,bash]
----
dotnet run --project src/BridgeService.Api
----

Escucha en `https://localhost:7001` y `http://localhost:7000` (`launchSettings.json`). El log de arranque avisa, sin parar, de lo que falte: `Ingest:WebPlatformId` (normal en local), contenedores de Storage (Entrega 2), `Frontend:BaseUrl`.

[source,bash]
----
curl -k https://localhost:7001/health          # → Healthy, o Degraded (ver abajo)
curl -k https://localhost:7001/health/ready    # comprueba la base
----

`/health` también mira el almacenamiento y la cola de correo (`T-BS-093`). Si Azurite no está levantado, si falta el contenedor privado o si hay correos reintentándose, responde `Degraded`, que sigue siendo un `200`, y el log dice qué dependencia falla. `/health/ready` solo mira la base: una caída del almacenamiento no saca al servicio de rotación.

[NOTE]
Si `dotnet run` protesta por el certificado HTTPS de desarrollo: `dotnet dev-certs https --trust` una vez. El frontend usa `secure: false` en su proxy, así que le da igual.

== El primer administrador

No hay usuario sembrado: la semilla crea roles, no cuentas. El único camino de alta sin sesión es el autorregistro, que nace `pending` con rol `viewer`; el primer administrador se promociona **una vez, a mano**, y a partir de ahí todo lo demás va por la API.

. Regístrate:
+
[source,bash]
----
curl -k -X POST https://localhost:7001/auth/register \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@tu-dominio.local","password":"UnaClaveLarga123","fullName":"Administrador"}'
----
+
En Mailpit aparece el correo `account_registered`.

. Promociónalo en la base. `ck_users_approved` exige `approved_by` y `approved_at` juntos o ninguno; como no hay nadie que apruebe, se deja ninguno:
+
[source,bash]
----
docker compose exec postgres psql -U bridge -d bridge -c "
UPDATE users
   SET status  = 'active',
       role_id = (SELECT id FROM roles WHERE name = 'administrator'),
       updated_at = now()
 WHERE email = 'admin@tu-dominio.local';"
----

. Entra:
+
[source,bash]
----
curl -k -X POST https://localhost:7001/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"admin@tu-dominio.local","password":"UnaClaveLarga123"}'
----
+
Devuelve `accessToken` (15 min) y deja el *refresh token* en una cookie. Con ese token, `GET /auth/me` debe listar permisos `recurso:accion` con `users:read`, `users:write`, `groups:write`, etc.

Desde aquí, los siguientes usuarios se crean con `POST /admin/users` (reciben invitación en Mailpit con el enlace para fijar contraseña) o se aprueban con `PUT /admin/users/{id}/approve`.

== Sembrar el catálogo y las cuentas

El catálogo entra **solo por empuje** (`ADR-BS-006`): no hay conexión a SinsaTools. En su lugar
está el simulador (`tools/IngestSimulator`, Fase 6), que lee el catálogo del mock del frontend
—250 productos, 752 versiones, 2.525 medios; los recuentos los declara el propio archivo
`Data/catalog.canonical.json`— y lo empuja por `/v1/ingest/catalog` igual que hará el emisor
real. Solo HTTP.

[source,bash]
----
export SIM_CLIENT_SECRET='<el secreto de §2.3>'
dotnet run --project tools/IngestSimulator -- demo
----

`demo` hace tres cosas, en orden, y cada una se puede lanzar sola:

. `seed-users` — registra por `/auth/register` las seis cuentas del mock (`admin@portal.dev` /
  `Admin123!`, `editor@`, `auditor@`, `viewer@`, `pending@`, `suspended@`, con las contraseñas
  de `fixtures.ts`) y las deja en su estado. **La primera vez se detiene** porque
  `admin@portal.dev` nace pendiente y nadie puede aprobarlo: imprime el `UPDATE` de §6 con ese
  correo. Ejecútalo y repite.
. `seed` — el catálogo en lotes `snapshot` de 200 (dos lotes), con `sequence`/`isLast`, y al
  final comprueba que lo que el servicio dice haber recibido cuadra con el canónico. Si no
  cuadra, sale con código 1.
. `grant` — crea el grupo «Demo — tres softwares» con todas las versiones de `VL-001`, `VL-002` y
  `VL-003` y mete en él a `viewer@portal.dev`. Es el escenario del criterio de aceptación.

Comprobación: en Mailpit hay seis correos de registro; `GET /admin/sync/status` con el token del
administrador da `catalogSummary.totalProducts = 250` e `isDataStale = false`.

Otras órdenes útiles:

[source,bash]
----
dotnet run --project tools/IngestSimulator -- seed --incomplete 10   # foto sin 25 productos: prueba la reconciliación
dotnet run --project tools/IngestSimulator -- seed --mode upsert     # sin reconciliación
dotnet run --project tools/IngestSimulator -- extract                # regenera el canónico desde fixtures.ts (Node ≥ 22.12)
dotnet run --project tools/IngestSimulator -- help
----

[NOTE]
Nadie lee bytes de los `storageUri` en la Entrega 1: el catálogo lista y el acceso se evalúa,
pero el *streaming* es Entrega 2. Por eso el `compose` no levanta Azurite. Los URI apuntan a la
cuenta y contenedores de Azurite por omisión (`--storage-account`, `--public-container`,
`--private-container` para otros).

== El frontend contra el servicio real

[source,bash]
----
cd ../Sin-PortalVideos
npm ci
npm start          # ng serve con proxy.conf.json → https://localhost:7001, reescribe /api → /
----

`http://localhost:4200`. El proxy quita el prefijo `/api`, así que el frontend llama `/api/auth/login` y el servicio recibe `/auth/login`. CORS ya admite `http://localhost:4200`.

`npm run start:mock` arranca **sin** servicio, contra la API simulada del propio frontend; útil para trabajar la interfaz, inútil para probar esto.

== Verificar que todo está bien

[source,bash]
----
./verify.sh        # Windows: .\verify.ps1
----

Es lo mismo que ejecuta la CI, en el mismo orden: `restore`, `format --verify-no-changes`, `build` en Release con avisos como errores, pruebas de arquitectura, todas las pruebas con cobertura, **la puerta de cobertura** (`tools/CoverageGate`: 80 % global y 100 % en las clases críticas de `EST-BS-08`, tumba el build) y `gitleaks` si está instalado. Si esto pasa y la CI falla, el que está mal es el script.

La Entrega 1 de punta a punta —base, API real, simulador, frontend sin mock y Playwright sobre el
criterio de aceptación (`T-BS-062`)—, y la Entrega 2 —lo mismo más Azurite, los blobs de la demo
y Playwright reproduciendo un vídeo por el proxy (`T-BS-074`)—:

[source,bash]
----
SIM_CLIENT_SECRET='<el secreto de §2.3>' ./tools/e2e-entrega1.sh      # KEEP=1 deja API y frontend levantados
SIM_CLIENT_SECRET='<el secreto de §2.3>' ./tools/e2e-entrega2.sh      # incluye la Entrega 1
----

Para reproducir a mano en el frontend hacen falta los bytes en Azurite; el simulador los sube
con los archivos de muestra del frontend (idempotente):

[source,bash]
----
dotnet run --project tools/IngestSimulator -- upload-blobs --samples ../Sin-PortalVideos/public/mock
# solo la demo (VL-001..003), mucho más rápido:
dotnet run --project tools/IngestSimulator -- upload-blobs --only-products VL-001,VL-002,VL-003 --samples ../Sin-PortalVideos/public/mock
----

Solo pruebas, en desarrollo:

[source,bash]
----
dotnet test

== Problemas habituales

[cols="2,3",options="header"]
|===
| Síntoma | Causa y arreglo

| `Falta 'ConnectionStrings:Postgres'` al hacer `dotnet ef` | No copiaste el `.example` (§2.1), o lo copiaste con otro nombre.
| `login` devuelve 500 y el log habla de `Jwt:PrivateKeyPem` | Falta la clave en user-secrets (§2.2). `dotnet user-secrets list --project src/BridgeService.Api` la muestra.
| `POST /v1/auth/token` → 401 | El `clientSecret` no corresponde al `ClientSecretHash` configurado. Regenera el par (§2.3) y pega el **resumen**, no el secreto.
| `POST /v1/ingest/catalog` → 422 por `storageUri` | La cuenta o el contenedor no coinciden con `Storage:*`, o la URI lleva *query string*. Mira el detalle del ítem en `GET /v1/ingest/{batchId}`.
| `POST /admin/users` → 500 `Frontend:BaseUrl` | Falta la clave (§2.5).
| `IntegrationTests` / `AcceptanceTests` fallan en el arranque del contenedor | Docker no está corriendo, o Testcontainers no encuentra el socket. `docker ps` primero.
| `dotnet build` falla por `IDE0005`, `CA*`, `CS157x` | Es a propósito: avisos = errores (`EST-BS`). Arregla el aviso, no lo silencies.
| `index.lock` en `.git` | Otro proceso de git dejó el candado. Comprueba que no hay ninguno y bórralo.
| `seed-users` sale con código 3 | Es lo esperado la primera vez: `admin@portal.dev` nace pendiente. Ejecuta el `UPDATE` que imprime y repite.
| `seed` → «Los recuentos NO cuadran» | Algún lote quedó `partial`: mira las líneas «·» que imprime (entidad y motivo) y `GET /v1/ingest/{ingestId}`. Lo habitual: `Storage:AccountUri` distinto del `--storage-account` del simulador (`DEC-BS-22`).
| Un correo no llega | No llega a ningún sitio: mira `http://localhost:8025`. Si tampoco está ahí, `notification_log` guarda el estado (`queued` / `sent` / `failed` con `error_detail`). Una fila `queued` con `attempt_count` mayor que cero se está reintentando: sale sola en cuanto Mailpit vuelve, en su `next_attempt_at` (`T-BS-090`).
| `POST /auth/login` o `/auth/register` → `429 RATE_LIMITED` en local | Tu `appsettings.Development.json` no tiene la sección `Auth:RateLimit` y valen los límites de producción (§2.6). Añádela, o espera lo que dice `Retry-After`.
| `SchemaParityTests` falla con 58 índices en vez de 59, o por las columnas de `notification_log` | Falta generar `MIG-BS-005` o regenerar el DDL derivado: `dotnet ef migrations add MIG_BS_005_NotificationRetries …` y `tools/regenerar_ddl_derivado.sh` (`changelog_modelo_datos`, entrada `MIG-BS-005`).
|===
