== El cotejo previo

Es la fase que hace demostrable la Entrega 1 sin SinsaTools. Se leyó `fixtures.ts` entero y se
**ejecutó**, no se estimó: los recuentos del plan no cuadran con el fixture actual (V6-01). Se
leyó la suite E2E existente del frontend para reutilizar sus `data-testid` y su `login`, y se
comprobó qué ve un usuario del catálogo según las decisiones de la Fase 4 (V6-03). Y se buscaron
las tres clases que `EST-BS-08` nombra al 100 %: no existen con esos nombres (V6-04).

El criterio de `T-BS-060` —«cuadran exactamente con el mock»— se cumple **contra el mock ejecutado**, no contra un número copiado: el extractor ejecuta `fixtures.ts` y el JSON canónico declara sus recuentos. Todo texto que decía 613/1.842 se corrige.
| `extract/export-fixtures.mts`, `catalog.canonical.json`
| ✅

| V6-02
| `plan_tareas` → `T-BS-060`: «convierte `fixtures.ts` en un JSON canónico»
| Convertir. No dice cómo
| **Se ejecuta el fixture con Node** (`--experimental-strip-types`, Node ≥ 22.12 que el frontend ya exige) y se vuelca; no se reimplementan sus fórmulas en C#. Una copia se desviaría a la primera edición del mock sin que nada avisara. El JSON resultante **va en git** (`tools/IngestSimulator/Data/catalog.canonical.json`, 1,4 MB, sin marca de tiempo para que solo cambie cuando cambie el fixture): `seed` no necesita Node ni el frontend, y la CI tampoco. `extract` lo regenera. Lo que el canónico añade al mock, y por qué, está en la cabecera del script: `sourceId` numéricos (el contrato los exige; `ext_version_id` es único en toda la base y el mock repite `EXT-V-1` por producto), `visibility` (imágenes públicas, resto privado) y la ruta de almacenamiento.
| `export-fixtures.mts`

| V6-03
| `plan_tareas` → `T-BS-062`: «un usuario de un grupo con acceso a tres softwares … **ve exactamente esos tres**»

| **No se filtra: V4-04 fijó que `versionsCount` no depende del usuario y el listado tampoco; lo que depende es `mediaCount` y la lista de medios.** El criterio se lee como: solo las versiones de esos tres productos muestran «View media (n)», con n igual a los medios del canónico; todo lo demás dice «No media»; y otro usuario sin grupo no ve medios en ninguna. Es lo que el JOIN concede. El oráculo de n es el JSON canónico, no la propia API.
| `bridge-acceptance.e2e.ts`

La puerta exige el 100 % a las seis y **falla si alguna no aparece en los informes**: un umbral sobre una clase ausente pasa en verde y no vale nada (el propio `ci.yml` lo advertía). `EST-BS-08` debe actualizar los nombres.

== Cómo se usa

[source,bash]
----
# Una vez: cuentas del mock + promoción del primer administrador (el simulador dice el SQL)
dotnet run --project tools/IngestSimulator -- seed-users
# Catálogo completo en dos lotes snapshot, con verificación de recuentos
SIM_CLIENT_SECRET=… dotnet run --project tools/IngestSimulator -- seed
# Grupo «Demo — tres softwares» con VL-001..003 y viewer@portal.dev dentro
dotnet run --project tools/IngestSimulator -- grant
# Todo lo anterior:
SIM_CLIENT_SECRET=… dotnet run --project tools/IngestSimulator -- demo
# Reconciliación:
SIM_CLIENT_SECRET=… dotnet run --project tools/IngestSimulator -- seed --incomplete 10
# Regenerar el canónico cuando cambie fixtures.ts:
dotnet run --project tools/IngestSimulator -- extract
# La Entrega 1 de punta a punta:
SIM_CLIENT_SECRET=… ./tools/e2e-entrega1.sh
----

== Hallazgos

[cols="1,5",options="header"]
|===
| # | Hallazgo

| H6-01
| ⚠️ *Los recuentos del plan estaban desactualizados* (V6-01). Nadie los volvió a calcular cuando cambió el fixture, y estaban copiados en tres sitios (plan, README, csproj). Regla: **los números que salen de un archivo se leen del archivo**, no se copian a la documentación; la documentación dice de dónde salen.

| H6-02
| 📌 *`EST-BS-08` nombra clases que no existen* (V6-04). El estándar se escribió antes que el código y nadie lo revisó al escribir las Fases 2 y 4. La puerta de cobertura lo habría dicho antes si hubiera existido desde la Fase 2, que es cuando el plan la ponía.

| H6-04
| ⚠️ *`verify.sh` nunca había pasado el paso de formato.* La primera ejecución completa (2026-09-23) sacó ~120 errores `IDE1006` en código de las Fases 2 a 6: la regla `campos_privados` del `.editorconfig` exigía `_camelCase` a **todo** campo privado, incluidos `const` y `static readonly`, y a toda variable local incluidas las `const`; el código, desde la Fase 2, usa PascalCase para esos casos —que es además la convención de .NET para constantes— de forma consistente. Se ajustó la regla al código, no el código a la regla: dos reglas nuevas más específicas (con `required_modifiers`) para constantes y estáticos de solo lectura privados, y una para constantes locales. Lo que sí eran errores del código (espacios, orden de `using`) lo arregló `dotnet format`. Lección: `verify.sh` debió correr al cerrar cada fase, no al final de la sexta; desde ahora es parte del cierre de fase.

| H6-03
| 📌 El frontend y el servicio discrepan en el «sin acceso» a los medios de una versión: `403` en el mock, `200` vacío en el real (V6-08). Es una divergencia mock/servicio, no un error de ninguno de los dos; se resolverá cuando la suite completa del frontend corra contra el servicio.
|===
